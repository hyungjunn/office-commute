# ADR 2. 매월 1일 초과근무 리포트 자동 발송 — 배치 + 메일 경로 신설

- 날짜: 2026-08-10
- 상태: 제안 (구현 전) — 관련: TODO.md 4번(본체), 3번 잔여(퇴사자), 6번 일부(타임아웃)
- 선행: ADR 1(주 단위 산정)로 리포트 수치 자체는 정합해졌다. 이제 그 수치를 **내보내는** 경로를 만든다.

## 배경

최종 목표는 "매월 1일 오전, 전월 초과근무 엑셀을 대표 이메일로 발송"이다. 현재 상태:

- **있는 것**: `OverTimeReportService.generateReport(YearMonth)` → `OverTimeReport`,
  `writeExcelReport(report, OutputStream)` → xlsx. 온디맨드 다운로드는 `OverTimeController`로 동작한다.
- **없는 것**: 스케줄러(`@EnableScheduling`·`@Scheduled` 미사용), 메일 의존성(`spring-boot-starter-mail` 없음),
  발송 이력, 실패 알림. 즉 이 절은 기존 코드 수정이 아니라 **경로 신설**이다.

이 저장소의 원칙은 "조용히 틀린 값 > 리포트가 안 나감"이다. 발송 경로 설계의 모든 갈림길에서
**틀린 값이 대표에게 도착하는 쪽을 막고, 지연·미발송은 사람에게 드러내는 쪽**을 고른다.

## 결정 요약

| 항목 | 결정 | 근거 |
|---|---|---|
| 스케줄러 | 앱 내 `@Scheduled` (외부 cron·Quartz 아님) | 배포는 단일 인스턴스 단일 jar(`docs/DEPLOYMENT.md` §2). 잡 스토어를 도입할 이유가 없다 |
| 중복 방지 | `report_dispatch` 테이블 + `UNIQUE(target_year_month)` | 배치 재시도와 수동 재실행이 겹쳐도 대표는 한 달에 한 통 |
| 재시도 | 매월 1~3일, 하루 4회(06/10/14/18시 KST), 같은 진입점 | "원장 대신 재시도"(TODO 2). 공휴일 API 다운을 흡수한다 |
| 미마감 게이트 | `unclosedCommuteCount > 0`이면 **대표 발송 보류**, 근태 관리자에게 교정 요청 | 미마감은 그 직원의 초과근무를 과소 집계한다 = 조용히 틀린 급여 근거 |
| 최종 실패 | 3일 20:00에 미발송 대상 점검 → 근태 관리자에게 알림 | "메일이 안 온 것"과 "실패한 것"이 구분돼야 한다 |
| 첨부 방식 | 메모리 버퍼(`ByteArrayResource`)에 **다 쓴 뒤** 첨부 | TODO의 "임시 파일" 지시에서 변경 — 아래 Step 3 참조 |
| 수동 재실행 | `POST /overtime/report/dispatch` (`@ManagerOnly`), 배치와 **같은 멱등 메서드** | 강제 플래그를 두지 않는다. 이미 SENT면 아무 일도 일어나지 않는다 |

## Step 0. 선행 확인 — 시작 전에 답이 있어야 하는 것

구현이 아니라 **차단 요인**이다. 코드를 쓰기 전에 확정한다.

1. **수신자 두 개**: 대표 메일 주소, 근태 관리자 메일 주소(복수 가능). 설정값으로 주입하며 코드에 박지 않는다.
2. **SMTP 계정**: 사내 메일 서버 or Gmail 앱 비밀번호. 첨부 용량 제한(수백 KB이므로 문제 없음).
3. **퇴사자 처리 (TODO 3 잔여)**: `Employee`에 퇴사 상태가 없어 `findAllWithTeam()`이 퇴사자를 0분 행으로
   싣는다. 온디맨드 조회에서는 "눈에 띄는 잡음"이지만, **대표에게 자동 발송되는 순간 잘못된 급여 근거 자료**가 된다.
   → 이 ADR의 범위 밖이되, **발송 시작 전에 처리하는 것을 권장**한다. 처리하지 않고 배치를 켜면
   첫 메일부터 퇴사자 행이 대표에게 간다는 사실을 명시적으로 수용한 것으로 본다.

## Step 1. 메일 인프라

**추가**
- `build.gradle`: `implementation 'org.springframework.boot:spring-boot-starter-mail'`
- `mail/ReportMailProperties`(`@ConfigurationProperties(prefix = "report.mail")`): `from`, `ceo`, `managers`(List)
- `mail/ReportMailer`: `JavaMailSender` + `MimeMessageHelper(message, true, "UTF-8")`로 첨부 발송.
  메서드는 용도별로 나눈다 — `sendMonthlyReport(...)`, `sendUnclosedCommuteWarning(...)`, `sendDispatchFailure(...)`.
  (플래그 인자로 분기하지 않는다 — 본문·수신자·제목이 전부 다르다.)
- `application-prod.yml`: `spring.mail.*`(host/port/username/password/starttls) + `report.mail.*` 전부 환경변수.
- 파일명 규칙(`2026년7월_초과근무보고서.xlsx`)은 현재 `OverTimeController`에 문자열로 박혀 있다.
  배치와 컨트롤러가 같은 이름을 내보내야 하므로 `OverTimeReportFileName.of(YearMonth)` 같은 한 곳으로 뽑고 양쪽이 쓴다.

**메일 본문에 반드시 들어갈 것** (수치를 열지 않고도 신뢰성을 판단할 수 있어야 한다)
- 대상 월, 대상자 수, 퇴근 미마감 건수, 산정 기준 한 줄("1일 8시간·1주 40시간 초과, 휴일근로 별도 트랙").

**고정할 테스트**: `ReportMailerTest`(Mockito `JavaMailSender`) — 첨부 파일명, 수신자, 제목에 대상 월이 들어가는지.
GreenMail 등 새 테스트 의존성은 도입하지 않는다.

## Step 2. 발송 이력 — 멱등성의 근거

**마이그레이션 `V12__report_dispatch.sql`** (원문 V11 — Step 0.3 선행 조치인 퇴사자 처리가
`V11__employee_work_end_date.sql`을 사용해 한 칸 밀림, 2026-08-10)

```sql
CREATE TABLE report_dispatch (
    report_dispatch_id BIGINT NOT NULL AUTO_INCREMENT,
    target_year_month CHAR(7) NOT NULL,          -- 'yyyy-MM'
    status VARCHAR(20) NOT NULL,                 -- IN_PROGRESS | SENT | FAILED
    attempt_count INT NOT NULL,
    last_attempted_at DATETIME(6) NOT NULL,
    sent_at DATETIME(6),
    last_failure_reason VARCHAR(1000),
    PRIMARY KEY (report_dispatch_id),
    CONSTRAINT uk_report_dispatch_year_month UNIQUE (target_year_month)
);
```

- `CHAR(7)` 'yyyy-MM' — `DATE`로 두면 "1일"이라는 존재하지 않는 날짜가 의미를 갖는 것처럼 보인다.
  JPA는 `YearMonth` ↔ `String` `AttributeConverter` 하나로 처리한다.
- `UNIQUE(target_year_month)`가 **중복 발송 방지의 유일한 하드 보증**이다. 나머지(스케줄 간격, 상태 전이)는
  전부 그 위의 편의 계층이다.
- **dev 프로파일은 Flyway가 꺼져 있고 `ddl-auto: create-drop`이다.** 마이그레이션과 엔티티를
  같은 커밋에 넣어야 dev 부팅과 prod 스키마가 어긋나지 않는다(V10 때와 같은 이유).

**도메인**: `domain/report/ReportDispatch` — 상태 전이를 엔티티가 소유한다.
`markSent(Instant)`, `markFailed(String reason, Instant)`(= `attemptCount++`), `isSent()`.

**고정할 테스트**: `ReportDispatchRepositoryTest`(기존 Testcontainers MySQL 패턴) —
같은 `yearMonth`로 두 번 삽입하면 두 번째가 제약 위반으로 실패한다.

## Step 3. 엑셀을 "다 만든 뒤" 첨부

배치는 `StreamingResponseBody` 컨트롤러를 타지 않는다 — 서비스를 직접 호출한다.

```java
ByteArrayOutputStream buffer = new ByteArrayOutputStream();
overTimeReportService.writeExcelReport(report, buffer);   // 여기서 던지면 메일은 시작조차 안 한다
byte[] attachment = buffer.toByteArray();
```

**TODO의 "임시 파일" 지시에서 변경한다.** 지시의 의도는 "부분 파일이 나가지 않게 = 다 쓴 뒤 첨부"이고,
메모리 버퍼도 그 의도를 동일하게 만족한다. 리포트는 직원 수 × 7열 규모(수백 KB)이고 `OverTimeReport`
전체가 이미 힙에 있으므로, 임시 파일은 크래시 시 잔여물·디스크 권한·정리 책임만 추가한다.
→ **재검토 조건**: 첨부가 수 MB급으로 커지거나(직원 수 급증, 일별 상세 시트 추가) 힙 압박이 관측되면 파일로 되돌린다.

## Step 4. 발송 유스케이스 — `OverTimeReportDispatchService`

진입점은 하나다. 배치도 수동 재실행도 이것을 부른다.

```java
public void dispatch(YearMonth target)
```

순서:

1. **이미 보냈는가** — `SENT`면 로그만 남기고 즉시 종료. (멱등의 본체)
2. **선점** — 행이 없으면 `IN_PROGRESS`로 INSERT. 유니크 위반이면 다른 실행이 선점한 것이므로 종료.
   기존 행이 `IN_PROGRESS`인데 `last_attempted_at`이 리스 시간(예: 30분) 이내면 종료, 넘었으면 회수한다
   (프로세스가 발송 도중 죽으면 그 달이 영원히 잠기는 것을 막는다).
3. **트랜잭션 밖에서** 리포트 생성 → 게이트 검사 → 엑셀 생성 → 메일 발송.
   `generateReport`는 공휴일 API를 라이브 호출하므로 **DB 트랜잭션 안에 두지 않는다**(TODO 6과 같은 이유).
4. **결과 기록** — 성공 `markSent`, 실패 `markFailed(reason)`. 각각 짧은 별도 트랜잭션.

**실패 사유는 분류해서 기록한다** (관리자가 "무엇을 고쳐야 하는지" 알아야 재시도가 의미를 갖는다):

| 사유 | 발생 | 관리자에게 나가는 메시지 |
|---|---|---|
| `UNCLOSED_COMMUTES` | 미마감 > 0 | "N건 마감 필요 — 마감하면 다음 재시도에서 자동 발송됩니다" + 미마감 목록 |
| `HOLIDAY_DATA_UNAVAILABLE` | `HolidayDataUnavailableException` | "공휴일 API 이용 불가 — 재시도 예정" (조치 불필요) |
| `MAIL_SEND_FAILED` | SMTP 오류 | "메일 발송 실패 — 계정/서버 확인 필요" |
| `UNEXPECTED` | 그 외 | 스택 로그 참조 |

**미마감 게이트가 이 설계의 핵심이다.** TODO 4의 마지막 미결 항목("건수가 0이 아닐 때 대표 발송을 막을지")을
**막는 쪽으로 확정한다.** 미마감 기록은 `workingMinutes = 0`으로 들어가 그 직원의 초과근무를 과소 집계하고,
이는 곧 임금 미지급이다. 엑셀 첫 행 경고만으로는 "대표가 경고를 읽었을 것"에 기대게 된다.

- 게이트에 걸리면: 대표 미발송, 관리자에게 **리포트 첨부 + 미마감 목록**을 보내 교정 요청, `FAILED` 기록.
- 재시도 창(1~3일) 안에 관리자가 마감하면 다음 시도에서 게이트를 통과해 **자동으로 대표에게 나간다.**
  이것이 재시도가 단순한 네트워크 리트라이 이상인 이유다.
- 미마감 목록을 본문에 담으려면 건수 쿼리만으로는 부족하다 →
  `CommuteHistoryRepository`에 `findUnclosedByWorkDateBetween`(사번·이름·근무일 프로젝션)을 추가한다.
  범위는 `countUnclosedCommutes`와 **반드시 동일**해야 한다(`MonthlyOverTimeCalculator.requiredRangeStart` ~ 말일).
  범위가 어긋나면 "건수는 3건인데 목록은 2건" 같은 모순이 나온다 — Review 1 발견 1과 같은 종류의 함정이다.

**고정할 테스트** (`OverTimeReportDispatchServiceTest`, Mockito):
- 이미 `SENT`면 메일러가 한 번도 호출되지 않는다
- 미마감 > 0이면 대표 메일은 안 나가고 관리자 경고만 나가며 `FAILED(UNCLOSED_COMMUTES)`로 기록된다
- `HolidayDataUnavailableException`이면 대표 미발송 + `FAILED`, 예외를 밖으로 던지지 않는다(스케줄러 스레드가 죽으면 안 된다)
- 성공하면 `SENT` + `sentAt`이 채워지고, 이어지는 두 번째 `dispatch`가 아무것도 하지 않는다
- 미마감 목록 조회 범위가 건수 조회 범위와 같다

## Step 5. 스케줄러

- `config/SchedulingConfig`: `@Configuration @EnableScheduling` (프로젝트 첫 도입).
  `@SpringBootApplication`에 붙이지 않는다 — 테스트 컨텍스트에서 배치가 같이 뜨는 것을 막기 위해 분리한다.
- `scheduler/OverTimeReportDispatchScheduler`: `@Profile("prod")`.
  dev/test에서 스케줄러 빈 자체가 만들어지지 않으므로 "켜기/끄기 플래그"가 필요 없다.

```java
private static final ZoneId KST = ZoneId.of("Asia/Seoul");

@Scheduled(cron = "0 0 6,10,14,18 1-3 * *", zone = "Asia/Seoul")
public void dispatchPreviousMonth() {
    dispatchService.dispatch(YearMonth.from(LocalDate.now(clock.withZone(KST))).minusMonths(1));
}
```

- **"전월"은 주입된 `Clock`에서 파생한다.** `LocalDate.now()` 무인자 호출 금지 — 테스트에서 시간을 고정할 수 없다.
- `Clock` 빈은 `systemDefaultZone()`이라 서버 TZ에 따라 달이 밀릴 수 있다. cron `zone`과 날짜 파생 zone을
  **둘 다 `Asia/Seoul`로 명시**해 서버 TZ와 무관하게 같은 달을 가리키게 한다.
- 총 12회 시도(1~3일 × 4회). 첫 시도는 1일 06:00 KST.

**최종 실패 알림** — 별도 스케줄로 분리한다(시도 로직에 "이번이 마지막인가" 조건을 섞지 않는다):

```java
@Scheduled(cron = "0 0 20 3 * *", zone = "Asia/Seoul")   // 3일 20:00, 마지막 시도 2시간 뒤
public void alertIfNotSent() { ... }  // 전월 이력이 SENT가 아니면 관리자에게 최종 실패 알림
```

**고정할 테스트**:
- `CronExpression.parse("0 0 6,10,14,18 1-3 * *").next(...)`로 1일 06:00이 첫 발화이고 4일에는 발화하지 않음을 고정
  (스프링 컨텍스트 없이 순수 단위 테스트)
- 고정 `Clock`(2026-09-01)으로 `dispatch(YearMonth.of(2026, 8))`가 호출되는지 — 특히 1월 1일 → 전년 12월 경계

## Step 6. 수동 재실행 엔드포인트

```
POST /overtime/report/dispatch?yearMonth=2026-07     @ManagerOnly
```

- 배치와 **완전히 같은** `dispatch(YearMonth)`를 호출한다. 강제 발송 플래그는 두지 않는다 —
  "이미 보낸 달을 한 번 더 보낸다"는 요구가 아직 없고, 있다면 그때 별도 유스케이스로 설계한다.
- 응답은 현재 발송 상태(`status`, `attemptCount`, `lastFailureReason`)를 그대로 돌려준다.
  관리자가 미마감을 고친 뒤 재시도를 기다리지 않고 즉시 확인할 수 있어야 한다.
- **`openapi.yml` 동기화 필수**(Spec-first, `openApiValidate`가 `check`에 물려 있다). 프론트 화면은 이번 범위 밖.

## 결과

- 대표는 **한 달에 정확히 한 통**을 받거나(유니크 제약), 아무것도 받지 않는다. 절반짜리 파일이나
  중복 메일은 구조적으로 나올 수 없다.
- 공휴일 API 다운은 리포트 실패가 아니라 **지연**이 된다 — fail-closed 예외가 `FAILED`로 기록되고
  최대 12회 재시도가 흡수한다. 이것이 TODO 2에서 원장(저장 계층)을 철회한 근거를 완성한다.
- 미마감 기록이 있으면 **대표 대신 근태 관리자**에게 간다. 교정하면 자동으로 대표에게 나간다.
- 조용한 실패가 없다: 3일 20:00 시점에 미발송이면 관리자에게 알림이 간다. "메일이 안 왔다"와
  "발송이 실패했다"가 구분된다.

## 감수하는 것 (명시적으로)

- **대표가 그 달 리포트를 못 받을 수 있다.** 3일까지 미마감이 안 고쳐지거나 SMTP가 계속 죽어 있으면 그렇다.
  이 문서의 원칙상 틀린 값보다 나은 결과이며, 관리자 알림으로 반드시 사람에게 드러난다.
- **단일 인스턴스 전제.** 다중 인스턴스로 확장하면 여러 노드가 같은 cron에 깨어난다. 그때도 중복 발송은
  유니크 선점이 막지만(선점 실패자는 그냥 종료), 리스 회수 로직이 경합할 수 있으므로 ShedLock류 도입을
  재검토한다. **재진입 조건: 인스턴스가 2개가 되는 시점.**
- **이미 SENT인 달의 데이터가 나중에 정정되어도 자동 재발송은 없다.** 재발송이 필요해지면 그때 설계한다.
