- 방식: 다각도 파인더 → 발견마다 독립 검증(adversarial verify). 후보 6건 중 3건 확정, 0건 반박.

## 확정 발견

### 1. [정확성] `countUnclosedCommutes`의 검사 범위가 확장된 조회 범위를 따라가지 못함

`OverTimeService.java:41-45`

`calculateOverTime`은 조회 범위를 "대상 월 1일이 속한 주의 월요일 ~ 월 말일"로 확장했다
(`OverTimeService.java:49`, 첫 주의 40h 판정에 전월 말 기록이 필요하므로). 그런데 리포트
신뢰성 지표인 `countUnclosedCommutes`는 여전히 **대상 월 1일~말일만** 검사한다:

```java
public long countUnclosedCommutes(YearMonth yearMonth) {
    return commuteHistoryRepository.countByWorkDateBetweenAndWorkEndTimeIsNull(
            yearMonth.atDay(1), yearMonth.atEndOfMonth()   // ← 스필오버 주(전월 말) 누락
    );
}
```

**실패 시나리오**: 직원이 2026-07-29(수)에 퇴근을 안 찍었다. 이 날은 8월 첫 주(7/27 월 ~
8/2 일)에 속하므로, 8월 리포트 생성 시 그 주의 40h 기반에 0분으로 들어가 주 잔여분
연장근로가 최대 8h 과소 집계된다. 그런데 `countUnclosedCommutes(2026-08)`은 8/1~8/31만
검사해 0을 반환하고, 엑셀 안내문은 "퇴근 미마감 0건 — 대상 월의 출근 기록이 모두
마감되었습니다"라고 출력한다. **과소 집계된 급여 근거 수치에 거짓 완결 보증이 붙는다** —
"조용히 틀린 값"이 가장 비싸다는 저장소 원칙에 정면으로 걸리는 케이스.

메서드 javadoc의 불변식("0이 아니면 과소 집계다")은 월 단위 조회이던 구 구현 기준으로
쓰인 것이다. 범위 확장 후에는 그 역(0이면 과소 집계 없음)이 성립하지 않게 됐는데,
javadoc도 코드도 갱신되지 않았다.

**수정 방향**: 검사 범위를 `calculateOverTime`이 실제 소비하는 범위(스필오버 월요일 ~
월 말일)와 일치시킨다. 아래 발견 2의 헬퍼 추출과 묶어 처리하면 두 메서드가 같은
범위 정의를 공유하게 되어 재발도 막는다. 회귀 테스트: 전월 말 스필오버 일자에 미마감
기록을 넣고 `countUnclosedCommutes(대상 월) > 0`을 고정.

### 2. [정리] 주 시작(월요일) 범위 로직이 두 클래스에 중복

`MonthlyOverTimeCalculator.java:40` / `OverTimeService.java:49`

```java
yearMonth.atDay(1).with(TemporalAdjusters.previousOrSame(DayOfWeek.MONDAY))
```

같은 식이 계산기(주 순회 시작점)와 서비스(조회 범위 시작점)에 각각 존재하고, "입력이
이 범위를 덮어야 한다"는 계약은 계산기 javadoc(19-20행)으로만 지켜지고 있다.

ADR 1이 명시했듯 주 시작 요일은 **취업규칙으로 정하는 사항이라 바뀔 수 있는 값**이다.
한쪽만 바꾸면 조회 범위가 첫 주를 덮지 못하는데, 누락된 날짜는 `getOrDefault(date, 0L)`
(`MonthlyOverTimeCalculator.java:47`)로 조용히 0분 처리되므로 **아무 에러 없이 첫 주
40h 기반이 과소 집계된다.** 급여 수치가 틀리는데 실패하는 것이 없다.

**수정 방향**: 계산기가 자신의 입력 계약을 소유하도록
`MonthlyOverTimeCalculator.requiredRangeStart(YearMonth)` 같은 static 헬퍼를 노출하고,
`OverTimeService`가 조회 범위(그리고 발견 1 수정 후에는 미마감 검사 범위)에 그것을
쓰게 한다. javadoc 계약이 컴파일 타임 공유 코드로 바뀐다.

### 3. [정리] `countBy…` javadoc이 이번 diff에서 삭제된 월 SUM 쿼리를 참조

`CommuteHistoryRepository.java:29`

> "이런 기록은 `workingMinutes = 0`으로 **초과근무 SUM에 들어가므로**…"

`findTotalWorkingMinutesByWorkDateBetween`(월 SUM)은 이번 diff에서
`findDailyWorkingMinutesByWorkDateBetween`(일별 프로젝션)으로 교체됐다. 주석이 가리키는
메커니즘이 더 이상 존재하지 않는다 — 유지보수자가 없는 SUM 집계를 찾아 헤매거나,
0분 행이 주 단위 산정에 미치는 영향을 잘못 추론할 수 있다. 급여 크리티컬 경로의
문서 표류이므로 "미마감 기록은 일별 0분 행으로 나타나 주 40h 기반을 깎는다" 취지로
갱신할 것.

## 검토했으나 문제없음 (주요 확인 지점)

- **이중가산 배제**: 일 8h 초과분은 `min(minutes, 480)`으로 주 기반에서 잘려 나가므로
  (58행) 일 초과와 주 초과가 같은 시간을 두 번 세지 않는다 — ADR 식과 일치.
- **휴일근로 분리**: 일요일·공휴일은 `continue`로 주 40h 기반에서 완전히 제외되고(50-56행)
  별도 트랙 집계. 토요일은 휴일이 아니므로 주 기반에 포함 — ADR 정책과 일치.
- **월 경계 귀속**: 일 단위 값은 `belongsToMonth`로 그 날의 달에(51, 59-61행), 주 잔여분은
  `weekEnd`(일요일)의 달에(64-67행) 귀속. 모든 시간이 정확히 한 번 집계된다.
- **전월 공휴일 조회**: 첫 주가 전월에 걸치면 전월 공휴일도 합쳐 조회
  (`findHolidays`, 80-87행). fail-closed 정책 유지.
