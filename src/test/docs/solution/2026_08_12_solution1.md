# Solution 1. 발송 서비스 리뷰 후속 — 낙관적 락 도입이 만든 결함과 그 수리

- 날짜: 2026-08-12
- 대상 브랜치: `claude/adr3-04-dispatch-service` (ADR 3 Step 4)
- 경위: ADR 3 Step 4 구현에 대한 1차 리뷰(7건) 지적을 반영하는 과정에서, 수정 자체가 새 결함
  8건을 들여왔다(2차 리뷰). 이 문서는 그 8건이 **무엇이 문제였고 어떻게 해결했는지**를 기록한다.
  1차 리뷰의 설계 방향(DELIVERY_COMMITTED, `@Version`, 스냅샷, 최종 예외 경계)은 전부 유지했다 —
  틀린 것은 방향이 아니라 JPA 세부와 예외 분류였다.

## 요약표

| # | 문제 | 심각도 | 해결 |
|---|---|---|---|
| 1 | `saveAndFlush` 반환 엔티티를 버려 이후 저장이 전부 낙관적 락 충돌 | **치명** — 행복 경로가 매달 깨짐 | 반환 엔티티 재대입 + 발송 확정 이후의 실패 처리를 갱신된 참조로 이동 |

| 8 | `generateReport`가 스냅샷을 우회하는 중복 경로로 잔존 | 낮음 | 스냅샷에 위임, `countUnclosedCommutes` 삭제 |

## 1. 치명 — 버려진 `saveAndFlush` 반환값과 낡은 `@Version`

**문제.** `runDispatch`가 발송 확정을 기록할 때 반환값을 버렸다:

```java
dispatch.commitDelivery(clock.instant());
reportDispatchRepository.saveAndFlush(dispatch);   // 반환 엔티티를 버림
...
recordSent(dispatch, ...);                          // 낡은 version으로 save → 항상 실패
```

이 서비스는 의도적으로 트랜잭션 밖에서 동작하므로(공휴일 API 라이브 호출 때문, ADR 3 Step 4)
`dispatch`는 detached 상태다. detached 엔티티의 save는 JPA **merge**이고, merge는 증가한
`@Version`을 **반환된 관리 엔티티에만** 반영한다. 전달한 객체의 version 필드는 그대로다.
따라서 DELIVERY_COMMITTED flush 직후부터 로컬 참조의 version은 DB보다 하나 낮고:

- **정상 발송마다** SENT 저장이 `OptimisticLockingFailureException`으로 실패 —
  모든 달이 DELIVERY_COMMITTED에 멈추고 `sentAt`이 기록되지 않는다.
- flush 후 SMTP가 실패하면 FAILED 기록도 같은 이유로 실패 — 종착 상태가 남아
  그 달이 **영구 잠김**(재시도 없음, 대표는 리포트를 못 받음).

Mockito 단위 테스트는 version 검사를 재현하지 않으므로 이 버그를 잡을 수 없었다.
전부 통과하는 테스트가 "동작한다"의 증거가 아니었던 사례다.

**해결.**

- 반환 엔티티를 재대입한다: `dispatch = reportDispatchRepository.saveAndFlush(dispatch);`
- 발송 확정 **이후**의 실패 처리(SMTP 실패 → FAILED 복귀)를 `runDispatch` 안으로 옮겼다.
  바깥 catch가 들고 있는 참조는 확정 flush 이전 것이라 version이 낡았기 때문이다.
- 발송 여부를 알 수 없는 예외(메일러의 비정형 예외)는 DELIVERY_COMMITTED를 유지한 채
  실패 알림만 보낸다 — 모르는 상태에서 재발송(중복 위험)보다 보류 + 사람 확인이 원칙에 맞다.

**고정한 테스트.** `recordSent_usesEntityReturnedByCommitFlush` — 확정 flush가 돌려준
(다른) 인스턴스로 SENT가 기록되는지 동일성(`isSameAs`)으로 검증한다. 반환값을 다시 버리는
회귀가 생기면 이 테스트가 깨진다.

## 2·3. 경합 패배는 장애가 아니다

**문제.** `@Version` 도입으로 재시도/리스 회수 경합의 패자는 `OptimisticLockingFailureException`을
맞는다 — 이것은 설계가 **의도한** 결과다. 그런데 이 예외가:

- `claim()`의 재선점 `saveAndFlush`에서 나오면 → 최종 경계까지 올라가 ERROR + 스택트레이스
  (최초 선점의 유니크 위반은 INFO로 처리하면서, 같은 의미의 경합이 장애처럼 기록됨)
- 발송 확정 flush에서 나오면 → `catch (Exception)`이 UNEXPECTED로 분류해 FAILED 기록 +
  **거짓 실패 알림 메일** (실제로는 이긴 실행이 그 달을 발송 중인데)

**해결.** 두 지점 모두 `OptimisticLockingFailureException`을 명시적으로 잡아 INFO 로그만 남기고
물러난다. 실패 기록도, 알림 메일도 내지 않는다 — 그 달의 소유권은 이긴 실행에 있다.

**고정한 테스트.** `concurrentRetryLoser_doesNotSend`(기존), `commitDeliveryLockLoser_stepsAsideQuietly`
— 패자가 대표 메일·실패 알림·이력 저장 어느 것도 하지 않음을 검증.

## 4. 미마감 게이트의 조인 의미 — LEFT JOIN

**문제.** 1차 리뷰는 "건수 쿼리와 목록 쿼리의 조인 의미가 다르다"였다. 수정은 건수를 목록에서
파생시켜 불일치는 없앴지만, 목록 쿼리가 `Employee`와의 내부 조인(세타 조인)이어서 게이트의
의미가 조용히 **좁아졌다**: `commute_history.employee_id`는 FK가 없고 nullable이라, 직원 행이
없는 고아 미마감 기록은 건수에서도 목록에서도 사라진다. 데이터가 깨졌을수록 게이트가 열리는
역전 — "조용히 틀린 값 > 리포트가 안 나감" 원칙의 정반대다.

**해결.** LEFT JOIN + `COALESCE(..., '(직원 정보 없음)')`. 고아 기록도 게이트에 걸리고,
관리자 경고 메일에 자리표시자로 드러난다. 그런 기록은 사람이 봐야 하는 데이터 문제다.

**고정한 테스트.** `findUnclosedByWorkDateBetween_keepsOrphanRows`.

## 5. 스냅샷 두 읽기의 순서 — 미마감을 먼저

**문제.** `generateReportSnapshot`은 집계(`calculateOverTime`)와 게이트(`findUnclosedCommutes`)를
별도 쿼리로 읽는다(비트랜잭션 — 공휴일 API 호출 때문에 묶을 수 없다). 기존 순서(집계 → 게이트)에선:
집계가 미마감 행을 0분으로 읽음 → 관리자가 그 기록을 마감 → 게이트 조회가 빈 목록을 봄 →
게이트 통과 → **과소 집계된 리포트가 대표에게 발송**. 게이트가 존재하는 이유 그 자체가 뚫린다.

**해결.** 읽기 순서를 뒤집었다(게이트 → 집계). 대상 월은 과거이므로 미마감 기록은 이후
**마감될 수만 있고 새로 열리지 않는다**. 따라서 집계가 미마감 행을 봤다면 그보다 먼저 읽은
게이트 목록에도 반드시 있다 — "게이트 통과 + 과소 집계" 조합이 구조적으로 불가능해진다.
(반대 방향의 잔여 창 — 게이트만 걸리고 집계는 정상 — 은 발송 보류일 뿐이라 원칙상 안전한 쪽이다.)

**고정한 테스트.** `generateReportSnapshot_readsUnclosedBeforeAggregation` (InOrder 검증 + 근거 주석).

## 6. 삭제된 DB 테스트의 복원

**문제.** 건수 쿼리를 지우면서 그 `@DataJpaTest`(연차 제외·마감 제외·범위 경계)도 함께 삭제됐고,
대체 쿼리 `findUnclosedByWorkDateBetween`은 Mockito 스텁으로만 존재했다 — 조인·`IS NULL`·
BETWEEN 경계·정렬·프로젝션 어느 것도 실제 SQL로 검증되지 않았다.

**해결.** `CommuteHistoryRepositoryTest`에 복원: 미마감만 반환(연차·마감·범위 밖 제외),
근무일 오름차순 정렬, 사번·이름 프로젝션, 고아 행 유지까지 실제 DB로 고정.

## 7. `markFailed` 이중 적용

**문제.** 미마감 분기에서 `recordFailure`의 save가 일시 장애로 던지면, 바깥 `catch (Exception)`이
`recordFailureAndNotify(UNEXPECTED)`를 불러 같은 엔티티에 `markFailed`가 **두 번** 적용됐다 —
시도 횟수 이중 집계, 진짜 사유(UNCLOSED_COMMUTES)가 UNEXPECTED로 덮임, 경고 메일 직후
엉뚱한 실패 알림 메일까지.

**해결.** 미마감 분기의 이력 저장을 자체 try/catch로 가드했다(경고 메일은 이미 나갔으므로
저장 실패는 로그로 남기고 다음 재시도에 맡긴다). 이제 `recordFailure`의 모든 호출 경로가
정확히 한 번만 가드된다.

**고정한 테스트.** `unclosedRecordPersistenceFailure_doesNotDoubleMark` —
`attemptCount == 1`, 사유가 UNCLOSED_COMMUTES로 유지, 실패 알림 미발송.

## 8. 중복 리포트 생성 경로 제거

**문제.** `generateReport`(컨트롤러/다운로드 경로)가 스냅샷을 우회하는 병렬 경로로 남아,
`countUnclosedCommutes`는 단일 호출자용 `.size()` 래퍼가 됐다. 두 경로는 곧 어긋난다.

**해결.** `generateReport`는 `generateReportSnapshot(yearMonth).report()`로 위임하고
`countUnclosedCommutes`를 삭제했다. 미마감 정보를 읽는 경로가 하나로 줄었다.

## 명시적으로 감수하는 것 (이번 수리에서 고치지 않음)

- **DELIVERY_COMMITTED 크래시 창.** 확정 flush와 SMTP 성공 사이에 프로세스가 죽으면 메일은
  안 갔는데 종착 상태가 남는다. 자동 재발송은 하지 않는다 — 급여 근거 문서의 중복 발송이
  유실보다 나쁘다는 선택. 대신 `claim()`이 이 상태(`DELIVERY_COMMITTED && sentAt == null`)를
  만나면 WARN으로 "수동 확인 필요"를 드러낸다. 조용히 묻히지는 않는다.
- **SMTP 예외 후 재시도의 중복 가능성.** 메일러가 예외를 던지면 미발송으로 보고 FAILED로
  되돌린다. 서버가 수신한 뒤 타임아웃된 극단 케이스는 이론상 중복이 가능하나, JavaMail 예외의
  절대다수는 미발송이고, 이 창을 없애려면 유실 쪽을 넓혀야 한다.
- **읽기 순서 불변식의 전제.** 5번의 안전성은 "대상 월 미마감 기록은 사후에 닫히기만 한다"에
  기댄다. 과거 월 출근 기록을 새로 만드는 기능(수동 데이터 보정 API 등)이 생기면 이 전제가
  깨지므로, 그때 스냅샷 전략을 재검토한다.

## 재발 방지 메모

- **detached 엔티티 + `@Version`이면 save/merge의 반환 엔티티만 유효하다.** 전달 인자를 계속
  쓰면 다음 저장이 깨진다. 이번 치명 버그의 뿌리이자, 트랜잭션 없는 서비스에서 반복되기 쉬운 패턴.
- **낙관적 락을 도입하면 그 예외의 "정상 경로"를 함께 설계해야 한다.** 충돌 예외를 기본
  실패 처리에 흘려보내면 정상 경합이 장애 알림으로 둔갑한다.
- **리뷰 지적을 고칠 때는 지적문이 아니라 코드의 원래 의도(ADR)를 컨텍스트로 삼는다.**
  이번 8건 전부, 지적 문장만 보고 국소 수정한 결과였다.
